# Julia Context OS × Domain Provider Binding Architecture v1.0

> Status: FROZEN CANDIDATE  
> Phase: F4.3-pre — Architecture Decision Phase  
> Date: 2026-07-31  
> Scope: Julia Agent generic runtime boundary, domain provider model, financial domain repositioning

## 1. Executive Summary

`julia_agent` is a general-purpose Agent Runtime architecture. It is not a financial-only agent.

Financial analysis is the first production domain, not the identity of the project. Future domains may include healthcare, coding, personal assistant, research, robotics, and other specialized capability providers.

The architectural rule is:

```text
One Julia Cognitive Runtime.
One Julia Context OS.
Many Domain Providers.
No domain-specific duplicate Agent OS.
```

## 3. Four-Layer Julia Agent Model

### Layer 0 — Agent Kernel

Julia's core existence and continuity.

Includes:

- Identity OS;
- Memory OS;
- Context OS;
- Governance OS;
- Runtime Orchestration.

Properties:

- shared by all domains;
- not owned by any domain;
- provider-independent;
- guarded by cognitive ownership rules.

### Layer 1 — Cognitive Infrastructure

Julia's model-facing cognitive operating system.

Includes:

- Context Planning;
- Context Budgeting;
- Context Projection;
- Evidence Resolution;
- Provenance;
- Conflict Resolution;
- Provider Routing;
- Session Lifecycle.

This layer decides what Julia sees before reasoning.

### Layer 2 — Domain Providers

Domain providers expose facts, evidence, tools, and capability results.

Examples:

```text
financial/
  Market State
  Theme Engine
  Event Engine
  Stock Evidence
  Risk Signal

healthcare/     # future possible domain
  Medical Knowledge
  Patient Data Adapter
  Clinical Evidence
  Care Plan Evidence

coding/         # future possible domain
  Repository Context
  Code Analysis
  CI/CD Evidence
  Issue/PR Tools
```

A domain provider may provide:

- facts;
- evidence;
- capability results;
- domain object references;
- domain governance metadata.

A domain provider must not own:

- Context OS;
- Memory OS;
- learning loop;
- prompt assembly;
- Julia identity;
- Julia action governance.

### Layer 3 — Application Surfaces

Human-facing or system-facing surfaces.

Examples:

- Analyst Workbench;
- Health Companion UI;
- Developer Assistant UI;
- Personal Assistant UI;
- Voice surface;
- mobile surface.

Application surfaces send intent pointers and object references. They do not send large context payloads and do not perform reasoning.

## 4. Context Authority Rule

All model-visible context must pass through Julia Context OS.

Correct path:

```text
User / Workbench Action
        ↓
Julia Runtime
        ↓
Context OS
        ↓
Context Planner
        ↓
Domain Context Request
        ↓
Domain Provider
        ↓
ContextBlock candidates
        ↓
Context Budget / Provenance / Projection
        ↓
Provider Input
```

Forbidden path:

```text
Domain
  ↓
Prompt / Provider Input
```

Forbidden path:

```text
Application Surface
  ↓
Large Context Payload
  ↓
Provider Input
```

## 5. Domain Provider Contract

### 5.1 DomainContextRequest

A request generated by Julia Context OS.

```python
@dataclass(frozen=True, slots=True)
class DomainContextRequest:
    request_id: str
    domain: str                       # financial / healthcare / coding / ...
    cognitive_scope: str              # e.g. financial_analysis
    intent: str                       # deep_dive / research / risk_review / ...
    object_type: str | None           # theme / stock / event / patient_record / repo / ...
    object_id: str | None
    evidence_intents: tuple[str, ...]
    exclusions: tuple[str, ...]
    budget_hint: int
    session_id: str | None
    trade_date: str | None            # domain-specific optional field; financial only
```

### 5.2 DomainContextProvider

```python
class DomainContextProvider(Protocol):
    domain: str

    def provide(self, request: DomainContextRequest) -> tuple[ContextBlock, ...]:
        ...
```

### 5.3 ContextBlock Requirements

Every returned block must carry:

- `block_id`;
- `block_type`;
- `content`;
- `source_refs`;
- `evidence_ids`;
- `authority_score`;
- `metadata.domain`;
- `metadata.object_type` when applicable;
- `metadata.object_id` when applicable.

Financial provider blocks must preserve `EvidenceRef` identity in either `evidence_ids` or `source_refs`.

## 6. Workbench Action Contract

Workbench actions carry object pointers, not context payloads.

Correct:

```json
{
  "type": "analyst_action",
  "payload": {
    "action": "ask_why",
    "object_type": "theme",
    "object_id": "9043089",
    "trade_date": "2026-07-31",
    "session_id": "session-1"
  }
}
```

Forbidden:

```json
{
  "type": "analyst_action",
  "payload": {
    "action": "ask_why",
    "theme": { "...": "full theme card" },
    "events": ["full event payloads"],
    "stocks": ["full stock payloads"],
    "evidence": ["full evidence bundles"]
  }
}
```

Reason:

- UI must not become a context builder;
- Context OS must decide what to load;
- evidence must remain backend-governed;
- budget and provenance must remain centralized.

## 7. Financial Domain Repositioning

Financial analysis remains a first production domain.

Correct role:

```text
Financial Domain Provider
```

Incorrect role:

```text
Financial Context OS
Financial Memory OS
Financial Agent Runtime
```

The existing `runtime/capability/financial/` package provides typed contracts, read-only clients, deterministic workflows, and interaction surfaces. Its long-term role is to expose Financial Domain Provider capabilities to Julia Context OS.

## 10. Non-Goals

This architecture freeze does not:

- merge the full runtime snapshot into `main`;
- implement healthcare/coding providers;
- add new UI features;
- add voice;
- add memory writes;
- alter trading/financial decision boundaries;
- approve any domain to bypass Julia Context OS.
